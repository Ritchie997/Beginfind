# План: публичная клиентская версия AllTell

Этот документ фиксирует целевое направление, текущий статус реализации и
дальнейшие этапы. Перед началом каждого этапа сверяйте его с актуальным кодом
и уточняйте детали интерфейса, которых нет в исходном запросе.

## Цель и границы

У AllTell будет две переключаемые поверхности:

1. **Основа / клиентская версия** — публичный сайт для читателей. Открытые
   статьи Antropedia можно читать без регистрации.
2. **Админ-панель** — существующее авторизованное рабочее приложение: создание
   и редактирование статей, настройки, управление серверами и другие имеющиеся
   инструменты.

Админ-панель рассматривается как отдельный рабочий режим поверх общей основы,
а не как целевая страница для читателя. Между режимами есть явный переключатель
в шапке/навигации. Ссылка, которой делятся статьёй, всегда открывает публичную
сторону; она не должна приводить в админ-панель и требовать вход для открытой
статьи.

**Минимальный объём первой реализации:**

- сделать реальной публичную основу вместо статического демо;
- подключить к ней Antropedia как доступную для чтения витрину;
- разрешить анонимное чтение открытых статей, сохранив ограничения закрытых
  статей/слоёв;
- направлять share-ссылки статей в публичный просмотр;
- оставить все операции редактирования и администрирования за текущей
  авторизацией.

Полноценные публичные сообщества, действия в галерее, новые профили, форма
регистрации в публичном интерфейсе и перенос всего админского функционала в
основу не входят в первый этап. Страницы серверов и галереи могут оставаться
заглушками/этапом позже, пока не согласован отдельный объём.

## Что есть сейчас

- `public/site/*.html` и `public/site/site.js` — самостоятельный статический
  макет. В `site.js` прямо указано, что запросов к API нет; карточки, поиск,
  лайки и загрузка ещё не подключены к данным.
- `public/index.html` — приложение админ-панели. `/admin-panel` отдаёт его,
  `/index.html` сохранён как прямой legacy-вход, а SPA fallback поддерживает
  прежние административные URL.
- Админское чтение статей реализовано в `public/antropedia.js`; внутренний URL
  статьи использует `/admin-panel/antropedia/:slug`, а share — публичный
  `/antropedia/:slug`.
- `GET /api/articles`, `/api/articles/browse` и `GET /api/articles/:id`
  защищены `authenticateToken` и `checkApproved`. Витрина и обычный просмотр
  пока не доступны гостю.
- Доступ к статье/слою централизован в
  `src/services/article-layers.js`: админские запросы используют резолвер
  пользователя, а гостевые — отдельный `resolvePublicArticleLayers` без
  фиктивного пользователя. Статьи и их слои могут быть закрыты по ролям.
- Лайки, комментарии, реакции, закладки, граф, расширенные метаданные и
  редакторские данные используют авторизованные API. Публичное чтение не
  должно случайно открыть запись или приватные поля.

Проверяемые исходники: `src/server.js`, `src/routes/pages.routes.js`,
`src/routes/articles.routes.js`, `src/services/article-layers.js`,
`src/services/articles-store.js`, `public/antropedia.js`,
`public/spa-router.js`, `public/site/*.html`, `public/site/site.js`.

## Адресная модель

Канонические пути первой реализации:

| Назначение | Канонический путь |
| --- | --- |
| Публичная главная / основа | `/` |
| Публичная Antropedia | `/antropedia` |
| Публичная статья | `/antropedia/:slug` |
| Админ-панель | `/admin-panel` |
| Админское редактирование статьи | `/admin-panel/articles/:slug` либо существующий редакторный маршрут SPA |

Существующие `/site/*.html` оставлены рабочими legacy-страницами. `/index.html`
остаётся прямым статическим entry point админ-панели, а старые `.html` страницы
админки и прежние SPA paths продолжают отдавать её оболочку. Старые
`/antropedia/:slug` ссылки теперь получают публичную оболочку, а не HTML админки.

Маршруты настроены явно и до SPA catch-all. Статический ресурс не должен
попадать в fallback. Внутренние переходы по wiki-ссылкам публичной статьи
должны сохранять публичный префикс; переход в редактор — только через кнопку
админ-режима и с существующей проверкой прав.

## План работ

### Этап 1. Контракты и маршруты — выполнен

Выполнено в первом routing change:

- `/` отдаёт публичную главную страницу `public/site/index.html`.
- `/antropedia` и `/antropedia/:slug` отдают публичную оболочку
  `public/site/antropedia.html`; динамическую статью пока не загружает — это
  следующий этап.
- `/admin-panel` открывает существующее приложение админ-панели; внутри него
  работают `/admin-panel` и `/admin-panel/antropedia`; админский просмотр
  статьи использует `/admin-panel/antropedia/:slug`.
- `/index.html`, `/admin-panel.html`, `/dashboard.html`, `/articles.html`,
  `/tags.html`, `/roles.html`, `/settings.html`, старые `/site/*.html` и прежние
  SPA paths (`/dashboard`, `/articles`, `/tags`, `/servers` и другие) сохранены
  как совместимые входы/адреса. `/index.html` по-прежнему является прямым
  статическим входом в админку.
- Текущие кнопки перехода с публичных страниц ведут на `/admin-panel`.

Технически статика настроена с `index: false`, чтобы `/` отдавал публичную
страницу, а `/index.html` продолжал получать админский HTML. Совместимые
`.html` маршруты обслуживает `src/routes/pages.routes.js`; прочие legacy SPA URL
принимает общий fallback.

Ограничение совместимости: `/antropedia` и `/antropedia/:slug` раньше
использовались админской SPA. Поскольку это канонический публичный адрес
Antropedia и адреса пересылок, они теперь отдают публичную оболочку. Переходы
из админской навигации перенесены на `/admin-panel/antropedia`; внутренние URL
просмотра статьи используют `/admin-panel/antropedia/:slug`, а share-кнопка
сохраняет публичный `/antropedia/:slug`. Уже открытая
или закэшированная админская SPA может продолжать работать по старому адресу,
но новая загрузка этих URL теперь публичная.

HTTP-маршруты покрыты интеграционным тестом. Проверка browser
reload/back-forward остаётся частью ручной проверки на развёрнутом экземпляре.

### Этап 2. Безопасное публичное чтение статей — первая реализация API

- Реализовано: отдельные `GET /api/public/articles` (список, поиск по `q`,
  фильтр `tag`, пагинация) и `GET /api/public/articles/:slug`; существующие
  авторизованные endpoints не менялись.
- Реализовано: используется общий нормализатор слоёв и отдельное правило
  гостевого доступа. Открытый legacy-слой виден; слой рядом с закрытыми
  ролями доступен гостю только с явным `public: true`. Если нет доступного
  публичного слоя, одиночный endpoint отвечает нейтральным 404, список,
  поиск, тег-фильтр и `total` не учитывают статью.
- Реализовано: ответ строится из allowlist полей выбранного публичного слоя,
  без сырых `layers`, ролей, вложений, авторских/user IDs, серверных данных
  и прав. Интерактивные карты и вставки работ галереи пока опускаются из
  документа, чтобы не раскрывать ссылки на контент без публичной политики
  доступа.
- Остаётся: подключить публичный интерфейс к этим endpoints; отдельно
  спроектировать безопасное публичное чтение wiki-графа, карт и галереи.
- Изменяющие и социальные endpoints остаются авторизованными; гостевые
  write endpoints не добавлялись.

**Важно для гостя:** не вызывать `resolveArticleLayer` с фиктивным `user.id`.
Для публичных API используйте `resolvePublicArticleLayers`, который не
обращается к пользовательским ролям; ошибки чтения не должны трактоваться как
публичный доступ.

### Этап 3. Публичная Antropedia

- Подключить реальные данные к публичному списку/поиску/фильтрации и детальной
  странице вместо демонстрационных карточек.
- Переиспользовать существующий renderer блоков только если он работает без
  админских глобальных объектов и не выставляет закрытые данные; иначе выделить
  минимальный безопасный public renderer с тем же форматом документа.
- Обеспечить прямую загрузку и обновление URL `/antropedia/:slug`,
  обработку «не найдено», «закрыто», loading/empty/error и адаптивный layout.
- Wiki-ссылки и ссылки на карты/галерею вести в публичную поверхность; для
  пока не реализованных публичных доменов определить нейтральную страницу
  или понятное сообщение.
- Скрыть/не показывать фиктивные цифры и mock-карточки; если данные ещё не
  подключены, пометить их как демонстрационные, не выдавая за реальный контент.

### Этап 4. Переключение «Основа ↔ Админ-панель»

- Добавить заметный переключатель в публичную навигацию и админскую оболочку.
- Публичный режим доступен без входа; переход на админку показывает текущий
  интерфейс авторизации/админки, не ослабляя маршруты и API.
- При переключении максимально сохранить контекст: со страницы статьи
  переход в админский редактор возможен только для вошедшего пользователя,
  только при разрешении редактирования и с тем же slug.
- Если гостю показывается кнопка «Админ-панель», её цель — страницу входа/
  админки, а не экран регистрации для чтения статей.
- Учесть back/forward, мобильное меню, редиректы после входа и уже имеющуюся
  сессию; не создавать фиктивный профиль для гостя.

### Этап 5. Share URL и совместимость

- `AntropediaManager.getArticleUrlPath()`/`shareCurrentArticle()` уже используют
  канонический публичный URL; проверить и обновить остальные места генерации
  ссылок на статьи.
- Обновить все места, генерирующие ссылки на статью: карточки, wiki-ссылки,
  отчёты/уведомления/граф, ссылки из редактора, copy/share controls и любые
  URL в письмах/внешних каналах (поиск репозитория перед изменением).
- Старые внешние `/antropedia/:slug` адреса направить на публичное чтение.
- Отдельно проверить, что кнопки редактирования внутри админки продолжают
  открывать редактор, а не публичный экран.
- Настроить title/description/canonical/OG metadata для публичной статьи.
  Если нужны корректные preview-карточки мессенджеров, чистого клиентского JS
  может быть недостаточно: оценить серверные meta tags или другой механизм до
  обещания поддержки.

### Этап 6. Проверка и стабилизация

- Гость: открытая статья и её публичные wiki-ссылки открываются с прямого URL,
  без cookie/токена и без редиректа на вход.
- Гость: закрытая статья и закрытые слои недоступны; их заголовок, excerpt,
  image, теги, текст и наличие в поиске/каталоге не раскрываются.
- Вошедший пользователь без роли получает тот же публичный контент, но не
  закрытые слои; пользователь с ролью получает ровно разрешённый слой; админ
  видит только то, что разрешает существующая политика.
- Anonymous write-запросы для лайков/комментариев/редактирования/закладок
  остаются отвергнутыми.
- Прямой share URL, reload, старые ссылки, URL с якорем/кодированным slug,
  mobile nav, переключатель режимов, back/forward проверены.
- Админские редактор, вход, SPA маршруты, API и права не регрессировали.
- Ошибки чтения, невалидный slug, отсутствующие загрузки и недоступная статья
  дают корректные UI-состояния, без success-shaped ответа.

## Зависимости и порядок

```text
Согласовать URL/алиасы
      ↓
Явно разделить публичную и админскую оболочки
      ↓
Безопасный read-only API для гостя
      ↓
Публичный список и просмотр статьи
      ↓
Переключатель режимов и перевод share/wikilinks
      ↓
Совместимость, metadata и проверка прав
```

Публичная оболочка и API должны иметь ясные URL-контракты до переноса всех
ссылок. Этапы можно реализовывать небольшими PR; нельзя включать гостевой UI
раньше серверного фильтра по доступу.

## Не входит в первую очередь

- Переписывание админ-панели или перенос её функций на публичный сайт.
- Гостевая регистрация/создание аккаунта и публичная социальная запись.
- Полноценные публичные страницы серверов, сообщения/чаты, галерея и профили.
- Новая ролевая модель, изменение существующих политик доступа.
- SEO-серверный рендеринг, если отдельно не подтверждена потребность в
  социальных preview; проблема OG metadata должна быть оценена.

## Вопросы, требующие решения до реализации

1. **Решено:** публичная основа использует `/`, админка — `/admin-panel`;
   `/index.html` сохранён как совместимый вход в админку.
2. Закрытая статья для гостя должна выглядеть как 404 или показывать нейтральную
   страницу с приглашением войти?
3. Нужны ли на первом запуске реальные публичные preview карточки для
   социальных сетей (OG tags), или достаточно браузерного просмотра?
